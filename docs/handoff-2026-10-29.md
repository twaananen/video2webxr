## What the extension currently does

The renderer uses Three.js and a shared `VRPlayer`. YouTube metadata detection
selects projections; other sites use the extension toolbar to inject packaged
code into the active tab. Automatic content scripts target YouTube. The metadata
helper runs in the page's MAIN world, while the renderer uses the isolated world.

Supported projections are flat, mono/stereo 180° and 360°, cubemap, and mono/
stereo EAC. YouTube's equi-angular cubemap layout needs its own mapping; it is
not interchangeable with a simple equirectangular texture.

The quality UI has **Picture**, **Rendering** and **Comfort** tabs:

- Restrained five-tap sharpening, brightness, contrast and color adjustments.
  Sharpening clamps sampling to the current stereo eye/cubemap face. It is not
  AMD CAS or an AI upscaler. EAC's color conversion was corrected and neutral
  RGB output tested across all nine projections.
- Render-scale requests, optional fixed foveation and cadence matching when
  actual session capabilities support them. Unsupported controls are disabled.
- Eye swap, small horizontal/vertical stereo corrections, VR180 FOV calibration,
  level recentering and gaze-directed recentering for reclined viewing.
- Reset, explicit **Save for this video**, **Original picture** comparison and
  Recenter. Original picture affects processing, preserving stereo alignment.
- Source dimensions, estimated video fps, dropped-video-frame counts, XR
  callback rate, CPU timing, actual render-buffer dimensions and granted AA.
  CPU timing is not GPU timing; callback rate is not proof of panel refresh.

Defaults preserve a neutral picture: sharpening/brightness/alignment zero,
contrast/color 100%, recommended render scale, normal eye order, VR180 FOV 180°,
level recentering, and runtime-labelled rendering preferences. Nothing forces
YouTube to choose a particular source resolution. Its public quality-setting
API is not a supported solution; source quality remains the website's choice.

Saves use `chrome.storage.local`, not sync storage or a server. Saving is
explicit, with validation and visible failure feedback. Keys omit signed URL
parameters/fragments; YouTube retains its video ID. Generic videos sharing the
same page path share a profile. Permissions are `activeTab`, `scripting`,
`storage`; storage was added by the feature work.

These angular image corrections do not change physical IPD or binocular
overlap. There is no depth-estimated autofocus, reconstructed 6DoF viewpoint,
video frame interpolation or custom compositor reprojection.

## Two resolved bugs to preserve

### Playback flicker

Playing immersive video flashed/flickered, sometimes showing passthrough.
Paused video was almost stable; loading a new paused frame briefly triggered
flicker. Lower source quality, moving controls out of sight, AR-to-VR switching
and disabling AA did not resolve it. A basic Three.js video sample was stable.

An explicit GPU completion wait stopped flicker, removing it brought flicker
back, and restoring it stopped flicker again. The lighter `gl.flush()` also
passed a full-minute viewing test, followed by the installed local build and a
normal Chrome restart. The retained fix flushes draw commands **only in XR**
before submission. Do not remove it as an optimization without a new controlled
comparison on the target runtime.

### Settings panel froze/failed to appear

The playback canvas grew from 336 to 720 pixels high after its GPU texture had
already been allocated. Merely setting `needsUpdate` did not resize that GPU
storage; rendering produced `GL_INVALID_VALUE` (1281).

`VRControls.setSettingsPage()` now disposes/recreates the `CanvasTexture` when
height changes, updates the material map/geometry, and retains the texture for
same-sized tab switches. Earlier tests checked interaction state without
rendering the transition, so they missed the bug.

The regression now renders a visible panel through three complete cycles,
checking GL errors, context loss and advancing render frames. All 15 actions
passed in native Frame XR. **Tommi subsequently confirmed the settings panel
works in the headset.** This supersedes older notes that still list that
particular physical check as pending; it does not validate all image-quality
experiments or MatineeVR controls.

## Experiments: what was actually measured

### Per-app SteamVR resolution and refresh

The real Chrome app key is
`system.generated.openxr.google chrome 157.chrome`; targeting only its Steam
shortcut ID would miss it. Relevant OpenVR keys are `resolutionOverride`
(integer) and `preferredRefreshRate` (float).

- Default XR buffer: 3456×1728 total, 1728×1728 per eye.
- Asking only the web layer for 115% stayed capped at that size; 85% worked.
- SteamVR's 2160 per-eye override enlarged the buffer to **4096×2160**, giving
  **2048×2160 per eye**, rather than the requested 2160×2160.
- General WebGL texture/renderbuffer limits were 16384. The separate 4096-wide
  XR constraint's exact cause was not established.
- A 90 Hz request increased callback cadence, but it was not perfectly 90.
  The 120 Hz request did not consistently deliver 120 callbacks/s.

Representative eight-second 4K runs: about 71.5 callbacks/s at defaults; 86.1 at
the larger resolution/90 request; 72.0 at the larger resolution/120 request.
The final fully fetched 4K runs reported no video drops or buffering waits.
Most XR timing samples were `visible-blurred`, not a controlled head-motion test.

Both temporary per-app keys were removed afterward. The user's original global
refresh preference was preserved. **No new resolution/refresh preset was
installed as a default.**

### MSAA and image-space smoothing

The direct XR layer reported AA off, but the WebGL context supported four-sample
offscreen targets. Using the existing Three.js SMAA implementation, paused-frame
tests produced valid detailed images without GL errors. Twenty non-disjoint GPU
timer samples were collected per case.

Median GPU times for a single square target:

- 1728×1728: original 0.213 ms; MSAA 4× 1.176 ms; SMAA 0.822 ms.
- 2160×2160: original 0.417 ms; MSAA 4× 1.966 ms; SMAA 1.429 ms.

MSAA barely changed pixels within the video; SMAA changed edge pixels. This is
expected: MSAA primarily addresses geometry coverage, whereas an image-space
filter can soften encoded/projected outlines. Neither reconstructs lost source
detail. SMAA can also blur text or useful detail.

These numbers exclude live decoding, full stereo/compositor integration and
thermal steady state; p95 samples were considerably higher. Do not convert them
into a promise of headset fps. **Neither prototype is installed in the player.**
Custom minification filtering remains a later experiment, not an implemented
feature or a solution to software decoding pressure.

### Browser versus native video decoding

Chrome reported `FFmpegVideoDecoder`, `kIsPlatformVideoDecoder=false`, and an
empty hardware-decoding profile list for the tested H.264 sources. An earlier
YouTube Pearl check also identified software VP9 decoding.

The fully fetched synthetic 8K H.264 run still struggled: approximately 43.5
render callbacks/s, 173 video frames, 13 reported drops and nine waits in eight
seconds. Its complete 12-second source was buffered, eliminating transfer speed
as the explanation for that run. These were high-detail stress clips at roughly
49 Mbit/s (4K) and 203 Mbit/s (8K), not proof that every 8K video must fail.

Foveation reduces rendering work; it cannot remove full-frame software decoding
work. A supported browser hardware-decoding path is the more immediate 8K
opportunity. No undocumented acceleration switches or browser compilation were
used to claim a solution.

## Remaining platform blockers

### Composition layers: browser and runtime must agree

Browser implementations already exist, including Chrome. On Frame, Chrome's
OpenXR backend requires all of these runtime extensions, and all were absent:

```text
XR_KHR_composition_layer_cylinder
XR_KHR_composition_layer_equirect2
XR_KHR_composition_layer_cube
```

The session did not grant `layers`, and `XRMediaBinding` was absent. Exposed
constructors/methods alone do not prove usable support. The extension currently
hides `XRWebGLBinding.prototype.createProjectionLayer` in its isolated world so
Three.js uses the working legacy `XRWebGLLayer` path instead of selecting an
unusable projection layer and stalling.

Future native layer integration needs runtime support or a changed Chromium
gate, actual feature negotiation and successful submission, plus a safe legacy
fallback. Direct video layers could improve clarity/efficiency through fewer
sampling passes. A polyfill drawing into the same old eye buffer cannot provide
that native advantage. EAC remapping and picture processing complicate a direct
media-layer path.

### Foveation and refresh are not hardware impossibilities

A read-only runtime enumeration reported 48 OpenXR extensions, including native
eye gaze, fixed/eye-tracked foveation and display-refresh interfaces. The current
WebXR session exposed no usable foveation or refresh control. Native extension
advertisement does not guarantee every mode or rate request will succeed.

Browser/backend integration could retain the current renderer. Replacing
Three.js with another web framework alone cannot expose missing browser APIs.
Custom WebGL foveation is possible in principle, but adds rendering work and
stereo edge cases; first establish a GPU-bound workload. Verify the meaning of
the runtime-default foveation setting before enabling it on a new backend.

The compositor already handles head-motion reprojection. Missing composition
layers does not mean all reprojection is absent. Video motion interpolation,
depth-based reprojection and reconstructed viewpoints are separate features
with substantial additional requirements.

### Website integration and browser security

Generic playback depends on readable, non-DRM media and normal browser origin
rules. A new native player does not inherit a site's login/cookies, signed
manifests, or browser extension permissions. Do not add credential-forwarding
proxies or broad permissions as an assumed shortcut.

The dedicated Chrome XR launcher uses `--enable-features=OpenXR`, X11, touch
events, and an explicitly authorized **`--disable-seccomp-filter-sandbox`**
workaround for a SteamVR/Linux XR conflict. Namespace sandboxing remains; this
is not blanket `--no-sandbox`. The missing syscall filter is a material browser
security tradeoff. Preserve normal password storage and site permission prompts.

A SteamOS Beta 0.5.6 trial booted into an unusable headset view/input state; the
previous A/B deployment recovered Stable 0.4.5. Do not make an OS update/reboot
or custom browser build a routine prerequisite for continuing this work.

This version accepts existing local files/folders and rejects normal webpage
URLs. It is a companion player and comparison implementation, not a replacement
for signed-in YouTube playback. FramePlayerX was researched as another native
candidate but was not installed/tested here.

MatineeVR selected `/dev/video-dec0`, the Iris V4L2 hardware decoder, for 4K/8K
H.264 and 8K HEVC. Decode-only probes processed 60 frames in approximately
0.150/0.589/0.653 seconds respectively. An 8K H.264 offscreen Vulkan probe also
passed using Turnip on Adreno 750, without disabling the injection layer.
Its output target was only 1024×1024: these are throughput checks, not full
headset fps or a physical UX/audio/comfort validation.

## Suggested next work, with decision gates

1. **Focused visual baseline:** compare the existing runtime defaults with the
   higher resolution and a 90-rate request. Use normal footage, fine text,
   animated outlines, head turns and representative stereo video. Preserve
   original per-app values. Do not assume a 120 request is an improvement.
2. **Optional spatial edge smoothing:** integrate only if comparison shows a
   useful benefit. Prototype per-eye processing, retain Original comparison,
   measure real XR frame budget, and test eye/face seams, controls and repeated
   session/panel transitions. Keep neutral defaults until justified. Offscreen
   MSAA alone is not the answer to encoded character outlines.
3. **Decoder path and realistic high-resolution clips:** identify codec,
   actual decoder, buffering and GPU cost before tuning. Prefer an existing
   supported browser/runtime update or a native companion over a new player
   rewrite. Native website handoff would be separate integration work.
4. **Future capabilities:** after relevant stable browser/runtime updates,
   re-run real feature/session probes. Enable layer, foveation or refresh
   controls only when actually usable; keep fallback and clear UX explanations.
5. **Site improvements:** extend the retained local fork when a concrete site
   fails. Preserve the active-tab permission model and normal origin/security
   boundaries. No cross-site native bridge has been built.

Other discussed comparisons—CAS-style sharpening, depth-estimated autofocus,
synthetic 6DoF and advanced video interpolation—are not implemented by the
current controls. Their scope/algorithms remain separate from this next small
quality milestone. No recurring research schedule was created.
